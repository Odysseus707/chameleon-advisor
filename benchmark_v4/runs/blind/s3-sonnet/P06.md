The typical cause is that the container's entrypoint runs briefly and exits (e.g., a script that finishes, or no foreground process to keep it alive). To keep it running, override the command to something that blocks indefinitely.
Quick fixes depending on your setup:

When launching the container, set the command explicitly to keep it alive:

bashopenstack appcred create ...  # if not already set up

python-chi container create \
  --name my-container \
  --image your-image \
  --command "tail -f /dev/null"

If using the Chameleon chi.container Python API:

pythonimport chi.container as cs

c = cs.create_container(
    "my-container",
    image="your-image",
    command=["tail", "-f", "/dev/null"],
    # ... other args
)

If you don't control the base image's ENTRYPOINT/CMD but need it to persist, override at launch time rather than editing the image — same idea, just append a blocking command:

bash--command "sh -c 'tail -f /dev/null'"

If the image has no shell utilities (minimal/distroless), use something like:

bash--command "sleep infinity"
Why this works: CHI@Edge (built on Zun) tears down a container once its main process exits — there's no "keep container running after command finishes" flag. Giving it a long-running foreground process (tail -f /dev/null or sleep infinity) satisfies that requirement so the container stays up and you can then:
bashpython-chi container execute my-container --command "/bin/bash"
or via CLI:
bashopenstack appcontainer exec my-container /bin/bash
A few things worth checking if it's still exiting:

Confirm the image actually has tail or sleep available (Alpine-based images have both by default).
Check container logs (openstack appcontainer logs my-container) to see what the original entrypoint was doing before it exited — sometimes it's crashing rather than just finishing normally.
Make sure you're not also setting a restart policy that's fighting with a short-lived process.

UVC Webcam on CHI@Edge (Raspberry Pi) with OpenCV
1. Device profile
CHI@Edge containers need explicit device passthrough for /dev/video* — nothing is auto-mounted. In your chi-edge container create call (or JSON spec), add a device_profiles entry (or devices block depending on API version) pointing at the video device:
json{
  "name": "webcam-opencv",
  "image": "docker.io/yourrepo/opencv-webcam:latest",
  "device_profiles": ["usb-camera"],
  "workdir": "/app",
  "command": ["python3", "capture.py"]
}
usb-camera here refers to a device profile registered on the Pi via chi-edge-device-profiles (or the equivalent zun-based device mapping if you're going through python-chi/zunclient directly). Concretely this maps to something like:
json{
  "usb-camera": {
    "host_path": "/dev/video0",
    "container_path": "/dev/video0",
    "permissions": "rwm"
  }
}
If you're using python-chi directly instead of the portal:
pythonfrom chi import container

c = container.create_container(
    "webcam-opencv",
    image="yourrepo/opencv-webcam:latest",
    device_profiles=["usb-camera"],
)
Caveats:

UVC device enumeration order isn't guaranteed — plug in one camera at a time for testing, and confirm the node with v4l2-ctl --list-devices on the Pi (via SSH or the Horizon/CLI device access, since CHI@Edge nodes are usually not directly SSH-able — check your site's access model).
Some CHI@Edge sites restrict which device profiles are available per-node; check openstack appcontainer host list / the site docs for what's pre-registered. If usb-camera (or similar) isn't listed, you'll need to ask the CHI@Edge admins to register it, since regular users typically can't add device profiles themselves.

2. Container image
Base on a lightweight ARM-compatible image (Pi = arm64/armhf, so avoid amd64-only base images) with OpenCV and V4L2 support built in:
dockerfileFROM python:3.11-slim-bookworm

RUN apt-get update && apt-get install -y --no-install-recommends \
    libgl1 \
    libglib2.0-0 \
    v4l-utils \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir opencv-python-headless numpy

WORKDIR /app
COPY capture.py .

CMD ["python3", "capture.py"]
Use opencv-python-headless (not the full opencv-python), since there's no display/GUI in the container — you don't want the Qt/GTK GUI dependencies pulling in extra arm64 build pain.
Build on or for arm64 explicitly:
bashdocker buildx build --platform linux/arm64 -t yourrepo/opencv-webcam:latest --push .
3. Capture code
pythonimport cv2

cap = cv2.VideoCapture("/dev/video0", cv2.CAP_V4L2)
if not cap.isOpened():
    raise RuntimeError("Could not open /dev/video0 — check device passthrough")

cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 720)

ret, frame = cap.read()
if ret:
    cv2.imwrite("/app/output/frame.jpg", frame)
cap.release()
Mount an output volume (or push results somewhere reachable) since you won't have a live display — CHI@Edge containers are headless.
4. Common gotchas

Permissions: even with the device mapped in, the container's user needs read/write on /dev/video0. Run as root in the container (default for most base images) unless your site enforces non-root — if so, add the container user to a video-equivalent group inside the Dockerfile.
No /dev/video* at all: means either the profile isn't wired up, or the UVC camera isn't enumerating on the Pi (check dmesg | grep -i usb and lsusb at the host level if you have any host access, e.g., via IPMI/console).
Multiple video nodes per camera: many UVC cams expose /dev/video0 and /dev/video1 (metadata node) — OpenCV wants the actual capture node, usually the lower-numbered one, but confirm with v4l2-ctl --list-formats-ext -d /dev/videoN.

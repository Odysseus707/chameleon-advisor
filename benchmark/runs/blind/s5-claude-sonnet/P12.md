# Inject my public key so I can SSH in as root

CHI@Edge containers don't have a cloud-init/config-drive metadata service the way bare-metal or KVM instances on other Chameleon sites do, so you can't just pass `key_name=` to a reservation and expect it injected. The key has to get into the container's `~/.ssh/authorized_keys` either at image-build time or via the container's environment/command at launch time.

The practical pattern (and the one used in the CHI@Edge SSH tutorial images) is: build an image whose entrypoint script reads your public key from an environment variable and writes it to `/root/.ssh/authorized_keys` before starting `sshd`, then pass the key as an environment variable when you create the container.

```python
import chi
from chi import container

chi.use_site("CHI@Edge")

with open("/home/you/.ssh/id_rsa.pub") as f:
    pubkey = f.read().strip()

my_container = container.create_container(
    name="my-ssh-container",
    image="youruser/edge-ssh:latest",  # entrypoint writes $SSH_AUTHORIZED_KEYS to authorized_keys
    reservation_id=device_reservation_id,
    exposed_ports=[22],
    environment={"SSH_AUTHORIZED_KEYS": pubkey},
)
container.wait_for_active(my_container.uuid)
floating_ip = container.associate_floating_ip(my_container.uuid)
```

An entrypoint script inside the image would look roughly like this:

```bash
#!/bin/sh
mkdir -p /root/.ssh
echo "$SSH_AUTHORIZED_KEYS" > /root/.ssh/authorized_keys
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
exec /usr/sbin/sshd -D
```

If you don't control the image's entrypoint, the fallback is to bake the key directly into the Dockerfile with `RUN mkdir -p /root/.ssh && echo "ssh-rsa AAAA..." > /root/.ssh/authorized_keys` before pushing it — less flexible (one key, requires a rebuild to rotate), but works with a minimal image that just runs `sshd`. Either way, root login over SSH also requires `PermitRootLogin yes` in the image's `sshd_config`, since most base images disable it by default.

```python
import chi
from chi import lease, container
from datetime import timedelta

chi.use_site("CHI@Edge")
chi.set("project_name", "CHI-000000")

# Lease: build it, add the device reservation, then submit and block until active
l = lease.Lease("demo-lease", duration=timedelta(hours=10))
l.add_device_reservation(machine_name="raspberrypi4-64", count=1)
l.submit(wait_for_active=True)

# Container: reference the lease's device reservation directly, submit and block until active
my_container = container.Container(
    name="demo-app",
    image="python:3.9-slim",
    reservation_id=l.device_reservations[0]["id"],
    exposed_ports=[22],
    platform_version=2,
)
my_container.submit(wait_for_active=True)
```

Behavior is the same as the original: one 10-hour lease reserving a single `raspberrypi4-64` device, then a `demo-app` container built from `python:3.9-slim` scheduled against that reservation with port 22 exposed. The differences are purely style — `lease.Lease`/`container.Container` are objects you configure and then call `.submit()` on (with `wait_for_active=True` replacing the separate `lease.wait_for_active()` / polling calls), and the reservation ID comes off the lease object's `device_reservations` list instead of a separate `lease.get_device_reservation()` lookup. `chi.use_site` / `chi.set("project_name", ...)` are unchanged since they configure the client, not the imperative-vs-OO call style.

This isn't a mechanical find-and-replace — CHI@UC bare metal and CHI@Edge are different resource models, so the script has to be restructured, not just re-pointed at a new site.

Your CHI@UC script (roughly):

```python
import chi
from chi import lease, server

chi.use_site("CHI@UC")
chi.set("project_name", "YOUR_PROJECT")

reservations = []
lease.add_node_reservation(reservations, node_type="compute_skylake", count=1)
node_lease = lease.create_lease("my-lease", reservations)
lease.wait_for_active(node_lease["id"])
reservation_id = node_lease["reservations"][0]["id"]

my_server = server.create_server(
    "my-instance",
    reservation_id=reservation_id,
    image_name="CC-Ubuntu20.04",
)
server.wait_for_active(my_server.id)
```

reserves a whole physical x86 machine (Ironic bare metal) and boots a full-disk OS image on it via Nova (`create_server`).

CHI@Edge doesn't offer bare-metal OS access at all — it's a container-as-a-service testbed (Zun). There is no `node_type='compute_skylake'` equivalent, because CHI@Edge machines are ARM-class edge devices (Raspberry Pi, Jetson boards, etc.), not x86 servers, and you never get a full OS shell on the bare hardware — everything runs inside a container. The conversion:

```python
import chi
from chi import lease, container

chi.use_site("CHI@Edge")
chi.set("project_name", "YOUR_PROJECT")

# Reserve a device instead of a bare-metal node.
# machine_name replaces node_type, and takes an edge device type name
# (confirm the exact string with container.list_device_types()).
reservations = []
lease.add_device_reservation(reservations, count=1, machine_name="raspberrypi4-64")
device_lease = lease.create_lease("my-edge-lease", reservations)
lease.wait_for_active(device_lease["id"])
reservation_id = device_lease["reservations"][0]["id"]

# Launch a container instead of a full-OS server.
my_container = container.create_container(
    name="my-edge-container",
    image="python:3.9-slim",   # a container image, not a whole-disk OS image
    reservation_id=reservation_id,
    command=["python3", "app.py"],
)
container.wait_for_active(my_container.uuid)
```

Key mapping, and where it breaks down:
- `add_node_reservation(node_type=...)` -> `add_device_reservation(machine_name=...)`. You're picking from CHI@Edge's edge device inventory, not an x86 flavor — there's no `compute_skylake` analog.
- `create_server(image_name=...)` -> `create_container(image=...)`. `image_name` on CHI@UC refers to a whole-disk OS image (e.g. `CC-Ubuntu20.04`); on CHI@Edge, `image` is a container image pulled by Zun, and it must be built for the device's CPU architecture (arm64 for Raspberry Pi).
- If your original script relies on SSH-ing into a full OS, installing arbitrary system packages, or doing anything that needs bare-metal/root-on-hardware access, that workflow doesn't have a CHI@Edge equivalent — you're confined to what you put in the container image and what the container runtime allows.
- If you need hardware peripherals (Sense HAT, camera, GPIO), add `device_profiles=[...]` to `create_container` — there's no equivalent concept on the bare-metal side since you already had full hardware access there.

I'm not fully certain whether your specific CHI@Edge deployment currently requires the explicit `add_device_reservation`/lease step for every device or schedules directly from `create_container` for some shared devices — worth confirming against current CHI@Edge tutorials or `container.list_device_types()` before relying on it.

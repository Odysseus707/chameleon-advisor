# Two Raspberry Pi 4s, one lease, SSH-enabled containers

On CHI@Edge, devices are reserved through Blazar (like the other Chameleon sites) but the compute unit you launch is a **container** (Zun), not a bare-metal node or VM. To get two Pi 4s in a single lease, ask for a device reservation with `count=2` against the `raspberrypi4-64` machine type. That reservation covers two physical hosts; you then create one container against each host.

For SSH, CHI@Edge doesn't do cloud-init key injection the way KVM sites do. The common pattern is to use a container image that runs `sshd` and accepts your key via an environment variable — e.g. the `linuxserver/openssh-server` image, which takes `PUBLIC_KEY` and starts sshd with that key authorized. You must also list port 22 in `exposed_ports` at container creation, and attach a floating IP so it's reachable from outside.

```python
import chi
from chi import lease, container

chi.use_site("CHI@Edge")
chi.set("project_name", "<your-project>")

reservations = []
lease.add_device_reservation(reservations, count=2, machine_name="raspberrypi4-64")
start_date, end_date = lease.lease_duration(days=1)

my_lease = lease.create_lease("two-pi4-lease", reservations,
                               start_date=start_date, end_date=end_date)
lease_id = my_lease["id"]
lease.wait_for_active(lease_id)

reservation_id = lease.get_device_reservation(lease_id)

pub_key = open("/path/to/id_rsa.pub").read().strip()

containers = []
for i in range(2):
    c = container.create_container(
        f"pi4-ssh-{i}",
        image="linuxserver/openssh-server",
        reservation_id=reservation_id,
        exposed_ports=[22],
        environment={
            "PUBLIC_KEY": pub_key,
            "USER_NAME": "pi",
        },
    )
    container.associate_floating_ip(c.uuid)
    containers.append(c)

for c in containers:
    print(c.name, container.get_floating_ip(c.uuid))
```

Notes:
- Creating two containers against the same `reservation_id` lets the CHI@Edge scheduler place one container per available host in that reservation — you don't pick which physical Pi gets which container.
- If you need root login instead of the default user, check the image's env vars (`linuxserver/openssh-server` supports `SUDO_ACCESS`/`PUID`/`PGID`); building your own minimal sshd image gives more control if you specifically need `PermitRootLogin yes`.
- Double-check the exact `machine_name` string against the current CHI@Edge hardware catalog before running this — it has changed over time (e.g. `raspberrypi4-64` vs an older `raspberrypi4b`-style name).

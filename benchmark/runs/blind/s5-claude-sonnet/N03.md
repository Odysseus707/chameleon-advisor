```python
import chi
from chi import lease, container

chi.use_site("CHI@Edge")

reservations = []
lease.add_device_reservation(reservations, device_name="iot-rpi-cm4-02", count=1)
start_date, end_date = lease.lease_duration(hours=3)
l = lease.create_lease("sensehat-lease", reservations, start_date=start_date, end_date=end_date)
lease.wait_for_active(l["id"])
reservation_id = lease.get_device_reservation(l["id"])

c = container.create_container(
    "sensehat-container",
    image="your-i2c-tools-image",  # needs i2c-tools + your GPIO/sensor library
    reservation_id=reservation_id,
    device_profiles=["pi_sensehat"],
    privileged=True,
    exposed_ports=[22],
)
container.wait_for_active(c["uuid"])

# List everything answering on the I2C bus the Sense HAT sits on
container.execute(c["uuid"], "i2cdetect -y 1")
```

The GPIO caveat: CHI@Edge containers don't have `/proc/device-tree` populated the way the host OS does, and GPIO libraries like `RPi.GPIO` and `gpiozero` normally read that to auto-detect the board model — inside the container that detection fails or misidentifies the board. The fix is to not rely on auto-detection: pick a pin factory / backend explicitly instead of letting the library probe the device tree (e.g. gpiozero's `lgpio`-based pin factory), or use a library that talks to `/dev/gpiochip*` and `/dev/i2c-1` directly rather than through device-tree lookups. That's also why the container needs `privileged=True` (or, more narrowly, passthrough of `/dev/i2c-1` and `/dev/gpiomem`) — without device access the I2C bus isn't visible to `i2cdetect` at all, regardless of the device-tree issue.

`i2cdetect -y 1` will print the address grid; whatever addresses show up are the Sense HAT (B)'s onboard sensors (IMU, environmental sensor, joystick/ADC) — I won't guess exact addresses since that's exactly what running the command is for.
